这是一篇用于展示博客排版的示例文章。有些概念在阅读时似乎清楚，一旦需要亲手实现，隐藏的问题才会出现。一个范围足够小的项目，可以把这些问题变得具体。

## 只选择一个要理解的机制

如果想理解搜索，不必一开始就制作完整的搜索产品。先写一个程序，读取几段文本，根据关键词返回匹配结果，就能遇到分词、大小写、排序和空结果等问题。

项目的边界最好用一句话描述，并配上一个可以观察的结果。例如：“输入关键词，返回包含它的文章标题。”这个目标能够帮助判断哪些功能是当前需要的，哪些可以稍后再做。

界面、账户和部署都可能有学习价值，但它们未必服务于眼前的问题。缩小范围，是为了让每一步尝试都更容易解释。

## 先让最简单的版本工作

下面的示例仅用字符串包含关系进行匹配，适合观察最基本的数据流：

```js
function searchPosts(posts, query) {
  const keyword = query.trim().toLowerCase();
  if (!keyword) return [];

  return posts.filter((post) =>
    post.title.toLowerCase().includes(keyword)
  );
}
```

输入经过清理，再被用于筛选，最后返回结果。它没有处理相关性或复杂语言规则，但已经能够检验一个最小假设：标题中出现关键词时，文章会进入结果列表。

## 观察边界，比堆功能更有用

得到可运行的版本后，试着改变输入：空字符串会怎样？大小写不同会怎样？只有正文出现关键词会怎样？两个标题都匹配时，它们按什么顺序出现？

这些问题让实现的范围变得清楚。可以先记录行为，再决定哪些符合预期、哪些值得修改。不要把所有缺失能力都视为错误；有些只是最初选择的边界。

每次只增加一个机制，例如先搜索正文，再引入简单排序。这样，观察到变化时，更容易知道是什么产生了影响。

例如，最简单的排序可以先统计查询词在文章中出现了多少种：

$$
\operatorname{score}(q, d) = \sum_{w \in q} \mathbf{1}[w \in d]
$$

这里 $q$ 是查询词集合，$d$ 是文章中的词集合，指示函数在词语匹配时取 1，否则取 0。这个分数忽略了词序与词语的重要程度，却足以用来观察增加排序前后的变化。

## 把结果写回最初的问题

项目结束时，除了保存代码，也可以补上一段说明：最初想理解什么，实际验证了什么，仍然没有处理什么。这能避免把“程序运行成功”误当成“整个主题已经理解”。

小项目的价值不在规模，而在于它提供了可修改、可观察的对象。当一个抽象概念能被转成输入、规则与结果，下一轮阅读也会带着更准确的问题开始。
